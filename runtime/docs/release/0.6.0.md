# StackSpirit 0.6.0

**First public StackSpirit release — the runtime, CLI, desktop cockpit and local agent nodes.
Unreleased draft.**

StackSpirit is the free, MIT-licensed always-on home for AI coding agents: one Linux VPS or
always-on machine owns the databases, session logs and supervisor, and the desktop app, Web/PWA,
`stackspirit` CLI and MCP are the surfaces. Mac and Linux machines can join as outbound **agent
nodes** and run a local surface or opt-in offloaded work. StackSpirit drives stock harnesses
through their documented interfaces and never stores or reads their logins.

0.6.0 is the first public StackSpirit release and the first release of the consolidated
monorepo. It ships the always-on runtime, the `stackspirit` CLI and daemon (with the `vowp`
compatibility alias), the StackSpirit desktop cockpit and the local agent nodes. The last public
release was 0.4.0 on 2026-11-18; 0.5.0 was a private snapshot, not a public release.

> **Status: unreleased draft.** No release date has been set. The release workflow is
> tag-driven for `v0.6.0`, but no tag, GitHub release or registry publish exists for this draft.
> Read [Honest limits](#honest-limits) before using the desktop chat, clusters or the ASIF
> interchange for unattended or production-critical work.

## Install

### Prebuilt archives

The release builds four native targets:

| Platform | Architecture | StackSpirit archive | Legacy CLI archive |
|---|---|---|---|
| Linux (glibc 2.35 or newer) | x86_64 | `stackspirit-0.6.0-x86_64-unknown-linux-gnu.tar.gz` | `vowp-0.6.0-x86_64-unknown-linux-gnu.tar.gz` |
| Linux (glibc 2.35 or newer) | arm64 | `stackspirit-0.6.0-aarch64-unknown-linux-gnu.tar.gz` | `vowp-0.6.0-aarch64-unknown-linux-gnu.tar.gz` |
| macOS | Intel | `stackspirit-0.6.0-x86_64-apple-darwin.tar.gz` | `vowp-0.6.0-x86_64-apple-darwin.tar.gz` |
| macOS | Apple silicon | `stackspirit-0.6.0-aarch64-apple-darwin.tar.gz` | `vowp-0.6.0-aarch64-apple-darwin.tar.gz` |

A `stackspirit` archive contains `stackspirit`, `vowp`, `stackspirit-daemon`, `vowp-daemon`,
`LICENSE`, `README.md` and `THIRD-PARTY-LICENSES.md`. The legacy `vowp` archive is CLI-only and
contains `vowp` plus the same three documents. Both names are supported commands; `vowp` is the
compatibility alias with the same command tree, flags, exit codes and JSON.

Each archive has a matching `.sha256` file, and the release publishes one combined `SHA256SUMS`.
Download the archive, its checksum and the combined file from the release assets:

```sh
VERSION=0.6.0
TARGET=x86_64-unknown-linux-gnu   # or aarch64-unknown-linux-gnu, x86_64-apple-darwin, aarch64-apple-darwin
BASE=https://github.com/Stack-Spirit/stackspirit/releases/download/v$VERSION

curl -fLO "$BASE/stackspirit-$VERSION-$TARGET.tar.gz"
curl -fLO "$BASE/stackspirit-$VERSION-$TARGET.tar.gz.sha256"
curl -fLO "$BASE/SHA256SUMS"

sha256sum -c "stackspirit-$VERSION-$TARGET.tar.gz.sha256"   # macOS: shasum -a 256 -c ...
tar -xzf "stackspirit-$VERSION-$TARGET.tar.gz"
"./stackspirit-$VERSION-$TARGET/stackspirit" --version       # must print: stackspirit 0.6.0
"./stackspirit-$VERSION-$TARGET/vowp" --version               # must print: vowp 0.6.0
```

The Linux archives are built on Ubuntu 22.04 against glibc 2.35; musl systems such as Alpine are
not supported. The macOS archives are not code-signed or notarized, so Gatekeeper may ask you to
confirm the first run.

The same binary is used on the home, the control machine and an agent node. The archive includes
the hidden `agent gateway` listener the home starts for WSS; there is no separate `vowp-agent`
executable to install.

From a checkout, the installer can download the StackSpirit archive, verify the checksum, check
both CLI versions and install both names and both daemons. Use the `stackspirit` product mode;
`--no-service --no-cron --no-watchdog` keeps it a binary-only install. It installs without
`sudo` to `~/.local/bin` unless `--prefix` is given, and it keeps an existing legacy unit in
place rather than creating a second one:

```sh
./scripts/install.sh --product stackspirit --version 0.6.0 \
  --base-url https://github.com/Stack-Spirit/stackspirit/releases/download \
  --no-service --no-cron --no-watchdog
```

### npm

The npm package is a thin launcher: it contains no binary of its own and runs no install script.
npm installs exactly one prebuilt platform package beside it:

| Platform | Package |
|---|---|
| Linux x64 (glibc) | `@stackspirit/linux-x64` |
| Linux arm64 (glibc) | `@stackspirit/linux-arm64` |
| macOS x64 | `@stackspirit/darwin-x64` |
| macOS arm64 | `@stackspirit/darwin-arm64` |

```sh
npm install -g stackspirit
stackspirit --version       # stackspirit 0.6.0
vowp --version              # vowp 0.6.0
npx -y stackspirit --version
```

Requires Node.js 18 or newer. The package installs four commands: `stackspirit`,
`stackspirit-daemon`, `vowp` and `vowp-daemon`. `npx -y stackspirit mcp` with no flags starts a
read-only stdio MCP server; the writable server needs `--session`, `--surface` and
`--token-file` together.

The old `vowp` npm package is frozen. Uninstall it before installing `stackspirit`, because both
provide a global `vowp` command:

```sh
npm uninstall -g vowp
npm install -g stackspirit
```

Windows and musl/Alpine are rejected by the package. Use WSL 2 on Windows, or build from source
on musl.

### PyPI

The PyPI distribution is a set of four self-contained platform wheels. Each wheel carries
`stackspirit`, `vowp`, `stackspirit-daemon` and `vowp-daemon` and installs four console scripts.
There is no source distribution.

```sh
pip install stackspirit
stackspirit --version       # stackspirit 0.6.0
uvx stackspirit --version
```

The wheels cover `manylinux_2_35_x86_64`, `manylinux_2_35_aarch64`, `macosx_10_12_x86_64` and
`macosx_11_0_arm64`. musl, Windows and 32-bit systems have no wheel; build from source instead.

### Homebrew

The release job renders a filled `vowp` formula from the `vowp-<version>-<target>.tar.gz`
hashes and uploads it as an artifact. The formula source is
[`runtime/packaging/homebrew/vowp.rb`](../../packaging/homebrew/vowp.rb); it is intended for a
`homebrew-vowp` tap and installs the `vowp` command. The `stackspirit` formula
([`runtime/packaging/homebrew/stackspirit.rb`](../../packaging/homebrew/stackspirit.rb)) is a
private template and is not tapped.

This repository does not create or push a Homebrew tap. Until the owner publishes one,
`brew install` is not a supported installer for this draft; use an archive, npm, PyPI or a source
build. The tap steps are documented in
[`runtime/packaging/homebrew/README.md`](../../packaging/homebrew/README.md).

### Build from source

```sh
git clone https://github.com/Stack-Spirit/stackspirit.git
cd stackspirit/runtime
cargo build --release --locked --workspace
./target/release/stackspirit --version       # stackspirit 0.6.0
./target/release/vowp --version              # vowp 0.6.0

# Or install both CLI names and both daemons:
cargo install --path . --locked
cargo install --path crates/vowp-daemon --locked
```

Prerequisites are a stable Rust toolchain (the runtime requires Rust 1.85 or newer), `git`,
`tmux`, a C compiler/linker for the bundled SQLite build, and a harness such as Claude Code or
opencode installed and signed in. The [install guide](../guides/install.md) covers the home,
control-machine and agent-node setup.

### Desktop cockpit

The desktop app is built from the monorepo. It is not part of the archive, npm or PyPI artifacts
in this draft, and there is no signed or notarized desktop installer.

```sh
git clone https://github.com/Stack-Spirit/stackspirit.git
cd stackspirit
npm ci
node scripts/fetch-engine.mjs
(cd apps/spirit-desktop && npx tauri dev)
```

The desktop needs Node 22 and a current stable Rust toolchain. `node scripts/fetch-engine.mjs`
downloads and checksum-verifies the pinned `opencode` sidecar that the app bundles and
supervises as its local engine. See [`docs/DEV-SETUP.md`](../../../docs/DEV-SETUP.md) for the
container build and [`docs/HANDOFF-DESKTOP-UI.md`](../../../docs/HANDOFF-DESKTOP-UI.md) for the
UI handoff.

## Upgrade from 0.4.0

0.6.0 is a binary upgrade from the last public release, 0.4.0. The rebrand itself moves no data:
the `stackspirit` and `vowp` names share one command tree, existing `~/.vowp*` directories are
used in place, and `.vowp/` job directories, `vowp.db`, session logs, `/api/v1` routes, MCP tool
names and JSON tags keep their names.

The engine upgrade also applies the normal global database migration from schema 7 to schema 8.
The migration writes `backups/pre-0.8-<milliseconds>.db` before it changes the file; project
databases stay at schema 2. A 0.4.0 binary refuses a schema-8 file rather than misreading it.

### What changes and what stays

| Changes (primary name) | Stays (supported alias or frozen name) |
|---|---|
| `stackspirit` CLI and `stackspirit-daemon` | `vowp` and `vowp-daemon` installed beside them |
| `stackspirit.toml` for new repositories | `vowp.toml` is read when there is no `stackspirit.toml`; a conflict is reported, never silently resolved |
| `~/.stackspirit`, `~/.stackspirit-agent`, `~/.stackspirit-control` for new hosts | Existing `~/.vowp*` directories are used in place; data is never moved automatically |
| `STACKSPIRIT_HOME` and related variables | `VOWP_HOME` is still read and exported |
| `stackspirit` MCP key for new orchestrators | Existing orchestrators keep the `vowp` key |
| — | `.vowp/`, `vowp.db`, session logs, HTTP routes, MCP tool names and JSON tags |

### Upgrade steps

1. **Stop the supervisor and take a backup.**

   ```sh
   vowp down
   vowp backup
   cp -a ~/.vowp ~/vowp-pre-0.6.0-backup
   ```

   Keep the filesystem copy until you are satisfied with the upgrade.

2. **Install 0.6.0** over the old binaries with an archive, the installer, npm, PyPI or a source
   build. Keep both `stackspirit` and `vowp` (and both daemons); the old unit, agent transport,
   `--node` commands and stored orchestrator configs invoke the legacy names.

3. **Link the new names to the existing home.** The link bridge writes symlinks only and does not
   copy or rewrite data:

   ```sh
   stackspirit home migrate --link --dry-run
   stackspirit home migrate --link --yes
   ```

   If `~/.stackspirit` already exists as a real directory next to a real `~/.vowp`, the resolver
   refuses to choose one; stop and resolve it by hand. Moving the directory to `~/.stackspirit`
   is optional and is a separate `stackspirit home migrate --move --to ~/.stackspirit` step.

4. **Drain and replace the supervisor.**

   ```sh
   stackspirit up --replace
   stackspirit status --check
   stackspirit doctor
   stackspirit fleet status
   ```

   `up --replace` drains active work, applies any pending migration with no active children and
   starts the new binary. It admits no new work until the new supervisor owns the lock, and it
   does not kill a running run.

5. **Update each agent node.** Install the same 0.6.0 binaries and refresh the generated unit in
   place. No re-enrollment or surface re-pairing is needed:

   ```sh
   test -e ~/.stackspirit-agent || ln -s .vowp-agent ~/.stackspirit-agent
   stackspirit agent service install --now
   stackspirit agent status
   stackspirit agent doctor
   ```

   The installer updates the existing `vowp-agent` unit (`vowp-agent.service` on Linux,
   `dev.vowp.agent` on macOS) and exports both `STACKSPIRIT_HOME` and `VOWP_HOME`. Renaming the
   unit is a separate explicit step: `stackspirit agent service install --rename-unit --now`.

6. **Update desktop and control machines.** Existing host profiles, tunnels and the `/api/v1`
   endpoint are unchanged. New orchestrators use the `stackspirit` MCP key; existing orchestrators
   keep the `vowp` key.

### Rollback

Rollback is a binary rollback because the data layout is unchanged. A 0.4.0 binary cannot open
schema 8, so do not downgrade the live home. Stop the supervisor, restore the pre-upgrade copy
into a staging directory, verify it, and start the 0.4.0 binaries against that copy. Never roll
back by editing a database or deleting a session log.

The full sequence, including the optional directory move and the per-machine checks, is in
[`runtime/docs/guides/stackspirit-migration.md`](../guides/stackspirit-migration.md). The legacy
name policy is in [`runtime/docs/deprecation-policy.md`](../deprecation-policy.md): every legacy
name is supported for all of v6, and removal is a v7 decision.

## What is in 0.6.0

The complete changelog is in [`runtime/CHANGELOG.md`](../../CHANGELOG.md). This summary is grouped
by surface. Features that come from the 0.4.0 line are marked as carried forward; the desktop and
v0.5 work is new in this release.

### Desktop

- **Meadow is the only shell.** The desktop is one chat-first cockpit with a server card, global
  and per-project orchestrators, Workers, Inbox and Settings. Light and dark themes follow the
  system, the Meadow palette passes WCAG AA in both themes, and the classic frame has been
  removed.
- **One-time-password onboarding.** Adding a server scans and shows the host-key fingerprints and
  requires an explicit "I verified this fingerprint" confirmation. The app creates an app-owned
  ed25519 key (passphrase in the OS keychain), installs it with a single password login, can
  optionally turn off password authentication, and auto-connects after a verified install. The
  password is cleared before the install call and is never rendered, logged, stored or sent to a
  model. Settings → **Password login** retries the optional sshd step and reports `disabled`,
  `not_supported` or `failed` exactly.
- **Orchestrator chat.** The setup assistant is real on the bundled engine and returns the real
  final reply; it is non-streaming by design (see [Desktop and chat](#desktop-and-chat)). Local
  `global`/`project` chat attaches to the local orchestrator endpoint reported by the installed
  runtime, continues the newest host session when no native id is reported, and never creates a
  native session or silently falls back to the bundled engine. A one-click **Start** creates,
  reuses, moves or resumes the real runtime project orchestrator
  (`stackspirit orchestrator new ... --app opencode`) and falls back to the bundled engine only on
  `chat_not_configured`.
- **Chat controls.** One shared composer has a searchable, provider-grouped model picker with
  included free models and BYOK, **Manage models**, a reasoning-effort selector, image/file
  attachments, copy and date/time message chrome, and usage telemetry from the engine. The model
  picker is hidden when the engine reports no usable models, with a direct **Set up a model** path.
- **Server secrets.** Settings → Advanced → **Server secrets** lists, stores and revokes keys in
  the runtime's own vault through `stackspirit secret` (`set` over verified SSH stdin, `ls --json`,
  `rm --yes`). The card shows the name, `•••• last4`, update time and the storage mode reported by
  `secret ls --json` (`basic`, `vault_user` or `encrypted`). The value never appears in argv, the
  environment, a log or an error; the app does not encrypt the vault itself and never runs
  `secret upgrade` on its own.
- **Session Host and projects.** An explicit **Host** control moves an orchestrator between Home
  and a local node with `stackspirit orchestrator move`; the transport chip stays read-only. The
  sidebar **＋ Add project** runs `stackspirit project add` and can create the chat on the
  connected Mac by default.
- **Clusters V1.** Multiple saved servers stay independent by default. **Form a cluster** enrolls
  each worker over verified SSH, enables pooled `[offload]`, registers a backup schedule and
  offers a confirmation-gated **Promote backup to Home**. The sidebar shows pooled Load and
  `busy / pooled target`; the Server page shows Home and worker state, slots and the backup policy.
- **Inbox, History and BYOK.** Active-only project view with a History tab, global and project
  Inbox views with an unread badge and one-click or free-text answers, and local provider keys
  kept in a private mode-`0600` file instead of prompting the OS keychain. The desktop reuses the
  read-only Web cockpit through the same `SpiritBridge` contract.

### CLI

- **One command tree, two names.** `stackspirit` is the primary name and `vowp` is the
  compatibility alias. Both names are built into the archives, npm package and PyPI wheels, and
  both report the same version, flags, exit codes and JSON.
- **Orchestrator move.** `stackspirit orchestrator move <name> (--node <node> | --home)` validates
  the target, stops the old host, releases its lease, writes a handoff capsule and starts the
  orchestrator on the target with the same `SessionId` and home log. The agent consumes the move
  as a `Start`, and the session row's node and cwd follow it.
- **Orchestrator endpoint.** `stackspirit orchestrator endpoint <name> --json` and
  `stackspirit agent orchestrator endpoint <name> --json` return the typed
  `OrchestratorEndpoint` document. The app password appears only in the explicit local command's
  `--json` output, never in a card, snapshot, log or error.
- **One-step project bootstrap.** `stackspirit project add` accepts `--git <url>`, `--init` and
  `--orchestrator <app>`. It clones with argv-only git and a credential-free environment,
  initialises only an uninitialised checkout, registers it and returns one
  `{project,path,initialized,orchestrator}` summary.
- **Encrypted vault mode.** `stackspirit secret upgrade --encrypted` stores basic-mode values as
  age ciphertext under `~/.vowp/secrets/encrypted/` with a mode-`0600` `age.key`.
  `stackspirit secret set <NAME> --stdin` reads a value without a TTY, and
  `stackspirit secret ls --json` reports `mode`. `systemd-creds` is not implemented.
- **Pooled cluster capacity.** Admission checks a home run against home and an eligible offloaded
  run against the online worker node's slots and headroom. `capacity report`, `fleet status` and
  the snapshot carry an additive `cluster` card with `online_worker_nodes`, `target_workers`,
  `busy_workers`, CPU, memory and free disk.
- **On-demand retention.** `stackspirit gc --older-than <duration>` shortens the retention window
  for closed sessions and run output only, through the safe compaction path. It refuses a session
  with a live lease or a running job.
- **MCP.** `stackspirit mcp` is a stdio MCP server. With no flags it is read-only and exposes the
  fleet, queue, inbox, capacity and session read tools; the full server requires `--session`,
  `--surface` and `--token-file` together.

### Runtime and home

- **Live snapshot streams.** The daemon serves `GET /api/v1/jobs/stream`,
  `GET /api/v1/jobs/{id}/stream`, `GET /api/v1/cost/stream`, `GET /api/v1/inbox/stream` and
  `GET /api/v1/nodes/stream`, plus the existing board stream. Each sends one initial snapshot and
  then changed-only frames with heartbeats, `Cache-Control: no-store` and the existing polling
  fallback; the Web pages reconnect with bounded backoff and refresh after keeper actions.
- **Local agent nodes and surfaces (carried from 0.4.0).** A Mac or Linux machine can enroll as an
  outbound Ed25519 agent node, pair a local `stackspirit chat` or opencode orchestrator surface,
  and take opt-in offloaded jobs while the home remains the only writer. The optional WSS ingress
  is loopback-only behind the owner's TLS reverse proxy; a launchd/systemd-user agent service,
  surface rotation and replacement, verified push or git-bundle results, capacity history and
  live supervisor drain/upgrade are included.
- **ASIF 0.4 session interchange (carried from 0.4.0, review draft).**
  `stackspirit session export <id> --format asif` writes a deterministic `.asif.zip` through the
  published `vowp-asif 0.1.1` adapter, and `stackspirit session import <file> --format asif`
  creates one new idle session from a package, a standalone `session.json`, a directory or stdin.
  Export redacts host paths by default and accepts repeatable `--redact` literals; import reports
  declared losses and supports `--strict` and `--allow-loss`. The daemon serves a token-free
  download route, a loss preview and a token-gated upload page. ASIF 0.4 does not claim
  conformance, an exact or lossless round trip, portable continuation or native-harness import.

### Web and cloud

- **Web cockpit.** `apps/spirit-web` is a mobile-first PWA that reuses the Meadow UI. It is
  read-only, sends no browser token, and shows unavailable daemon data explicitly instead of
  inventing it. It can run against the loopback daemon through a proxy, or in clearly labelled
  preview mode with the shared `MockBridge`. The new snapshot streams keep the live pages current.
- **Optional account and relay.** The Web app's **Always-On Homes** route and the desktop cloud
  client add an optional StackSpirit account, an enrolled-machine list and a relay-backed cockpit.
  Local mode remains the default and needs no account, no cloud connection and no hosted service.
  The CLI adds `stackspirit login` (device code, or a pre-issued token on stdin),
  `logout`, `whoami`, `machines ls`, `ssh <machine>` over the relay, and
  `relay enroll|status|run|rotate-key`. The enrollment token is read from a file, stdin or
  `STACKSPIRIT_ENROLL_TOKEN`, never from a flag value.
- **Encrypted R2 backups.** `stackspirit backup push --recipient age1...` archives the home,
  encrypts it client-side with `age` and uploads only the ciphertext. `backup list` shows the
  account's encrypted objects, and
  `backup restore --identity <mode-0600 file> --to-home <fresh-home>` downloads, verifies the
  SHA-256, decrypts locally and verifies every file hash and row count before restoring. The
  private identity stays offline and is never uploaded; a push is capped at 64 MiB. The add-on is
  off by default and requires the optional cloud account and a relay-enrolled machine.

## Honest limits

These are the limits that matter for a first 0.6.0 user. They are taken from the current code, the
handoff and the recorded runs.

### Desktop and chat

- **The live D6 flip is an owner/Mac check.** The desktop probes now match the runtime's `0.4.0+`
  surface, but the **Local orchestrator** gate stays `Waiting` until the owner's Mac agent reports
  the required version and the gate becomes `Ready`. D6 actions remain disabled here, and no live
  Mac takeover or add run has been performed from this Linux host. The handoff's owner checklist
  run is outstanding.
- **Server chat stays gated.** Desktop Server `global`/`project` chat still returns the typed
  `chat_gated` gate. The transport chip is read-only and the app does not open its own SSH
  forward (owner decision A). Local chat uses the endpoint; the Server path is not enabled in this
  release.
- **Setup chat is non-streaming by design.** The production transport reports
  `streaming_supported: false`; the final assistant message is real but arrives as one complete
  message. Do not describe it as token-by-token until the owner records the event cadence.
- **Local chat depends on the installed runtime.** It attaches only when the runtime reports a
  local orchestrator endpoint; otherwise the app returns `chat_not_configured` and offers the
  bundled-engine path. The owner's Mac endpoint was live-verified on 2026-11-19, but no owner run
  of `scripts/verify-orchestrator-chat.mjs` has been recorded, so the Server half and the
  `message.part.*`/`session.idle` cadence remain unverified.
- **The desktop capability gates stay.** `LocalOrchestratorGate` and `AsifGate` remain until the
  remaining wiring lands; actions enable only when the probes are `Ready`. A version string alone
  never makes a gate Ready.
- **No live desktop smoke or signed bundle.** The Meadow desktop suite is recorded green in the
  handoff, but there is no signed/notarized desktop installer and no owner live desktop smoke for
  this draft. The macOS build and real OS-keychain round trip remain owner verification.

### Clusters and capacity

- **No last-backup timestamp.** `ClusterHealth` carries no observed backup time, so promotion
  shows the policy's maximum age (`freshness ≤ every`), never an invented "last backup" time.
- **Promotion needs the old Home.** Promotion requires the old Home to answer
  `stackspirit down --drain`; it cannot rescue an unreachable Home. A completed promotion shows
  the restored Home identity and offers an explicit **Connect to** action; it never switches the
  active server silently.
- **Pooled totals are computed.** The desktop cluster view computes pooled numbers from Home and
  the visible online workers, labels them `computed`, and says so in the UI. The sidebar Load in a
  cluster is pooled worker utilization (`busy / pooled target`), not the single-host RAM/CPU
  figure.
- **Cluster policy is preserved.** Forming a cluster writes `default = "any"` and
  `result_transport = "bundle"` but preserves an owner-set project placement and
  `max_remote_runs`. A Home profile with a non-default SSH port is refused; use port 22 or an SSH
  config alias on every worker.

### Platform and install

- **Windows is not a shipped target.** The release matrix has four targets: Linux x86_64/arm64 and
  macOS Intel/Apple silicon. The npm and PyPI packages reject Windows; use WSL 2 or build from
  source. Linux musl (for example Alpine) has no archive or wheel.
- **Archives are not signed.** The macOS archives are not code-signed or notarized, and the
  desktop has no signed/notarized installer. Gatekeeper may ask you to confirm the first run.
- **Homebrew is an artifact, not a tap.** The workflow renders a `vowp` formula, but this
  repository does not create or push a tap. Until the owner publishes one, `brew install` is not a
  supported installer.
- **Cloud is optional and separate.** The account, relay and encrypted R2 backup features need the
  StackSpirit cloud service and a relay-enrolled machine. Local mode is the default and does not
  require an account. The cloud backend is not part of this repository, and the R2 add-on is off
  by default.

### Interchange and secrets

- **ASIF 0.4 is a review draft.** Export/import reports declared losses and does not claim ASIF
  conformance, an exact or lossless round trip, portable continuation or native-harness import.
  Jobs, gates, leases and project rows are not in the package. The published
  `vowp-asif = "=0.1.1"` adapter resolves from crates.io; see
  [`runtime/docs/design/v0.4/asif-integration.md`](../design/v0.4/asif-integration.md).
- **Encrypted vault mode has no key management.** It protects an offline copy of the home that
  does not include `age.key`; it does not protect against code running as the same user. There is
  no key rotation, passphrase, hardware keystore or recovery path, the key is not backed up, and
  losing it loses every encrypted value. `systemd-creds` is not implemented.
- **Secret redaction is exact-value only.** A transformed or encoded copy, or a value printed by a
  harness in a turn, can escape redaction; command-gate evidence and the report/run mirror stay
  raw during a turn. The `secret_scan` gate is a backstop, not a guarantee. Harness logins remain
  under the harness's control.
- **Agent-node evidence is one owner run.** The live Mac smoke test recorded for the 0.4.0 line is
  a single owner run, not a multi-day soak, and it does not prove every macOS version or a daily
  operating checklist.

### Release state

- **Nothing is published.** There is no 0.6.0 tag, GitHub release, npm publish or PyPI publish.
  The release note is an unreleased draft and the release workflow creates only a draft until the
  owner publishes it.
